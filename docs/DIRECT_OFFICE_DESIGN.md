# 사무실 안에서 지시하고 실행하는 구조

설계일: 2026-10-21
상태: 구현 예정. v0.5의 복사 → GitHub 수동 접수 방식은 이 설계의 목표 동작이 아니다.

## 1. 사용자가 경험하는 흐름

1. PC에서 `start-office.bat`을 실행한다. 로컬 연결 서비스가 켜지고 기존 사무실 페이지를 연다.
2. 사무실의 **내 PC 연결**을 누른다. 최초 연결은 PC 실행기에서 승인한다. 브라우저가 로컬 네트워크 접근을 요청하면 허용한다.
3. 연결 상태가 확인되면 사무실에서 **출근**을 누른다. 서비스 시작과 근무 시작을 구분한다.
4. 직원 아바타를 선택하고 명령을 입력한 뒤 **업무 지시**를 누른다.
5. PC가 업무를 저장했다는 응답을 받으면 업무 카드가 생긴다. 해당 직원이 작업하고 결과가 검토함에 도착한다.
6. 같은 카드에서 추가 지시, 취소, 결과 확인을 한다. 퇴근도 사무실에서 처리한다.

명령 복사, ChatGPT에 재전달, GitHub Actions 화면 이동은 일상 업무에서 없앤다. 최초 CLI 설치와 ChatGPT 로그인, 필요 시 재로그인은 PC에서 진행한다. 웹에서 ChatGPT 비밀번호나 API 키를 받지 않는다.

예: 개발 직원 선택 → “첫 화면에 출근 버튼과 현재 근무 시간을 표시해줘” → 업무 지시 → 작업 중 → 변경안과 테스트 결과 확인.

## 2. 연결 방식 결정

**기본은 GitHub Pages 화면 + 같은 PC의 로컬 연결 서비스**다. 별도 외부 중계 서버나 월별 서버 비용 없이 시작한다. AI는 사용자 PC의 로그인된 Codex가 실행한다.

| 구성 | 책임 | 저장 위치 |
| --- | --- | --- |
| GitHub Pages 사무실 | 직원 선택, 지시, 작업 상태와 결과 표시 | 화면 코드·공개 자료는 GitHub |
| 로컬 연결 서비스 | 브라우저 연결 인증, 업무 저장, 출퇴근, 실행·취소 관리 | PC의 SQLite DB |
| Codex 실행 어댑터 | 역할·업무·허용 작업공간을 받아 실행 | PC 인증 저장소와 작업공간 |
| GitHub 동기화 | 검토된 공개 기록·문서·코드 보관 | 사용자 저장소 |

로컬 서비스는 `127.0.0.1`에만 바인딩한다. 초기 포트 후보는 43177이며 충돌 시 명확한 오류와 해결 방법을 보여준다. 임의 IP나 포트를 페이지가 자동 탐색하지 않는다.

GitHub Pages와 localhost는 출처가 달라 CORS·브라우저의 로컬 네트워크 접근 정책 검증이 필요하다. 지원을 가정하고 완료 처리하지 않는다. Chrome/Edge 실제 연결이 1차 출시 조건이다.

**대체 경로:** 직접 연결이 거부되면 “이 PC에서 사무실 열기”로 로컬 서비스가 제공하는 동일 UI를 연다. UI와 API가 같은 출처에서 동작하도록 한다. 이 경우 주소가 localhost로 바뀐다는 점을 안내한다. 명령 복사 방식으로 돌아가지 않는다. 브라우저 보안 기능을 끄게 하지 않는다.

모바일 원격 명령은 1차 범위에서 제외한다. 휴대전화의 localhost는 사용자 PC가 아니다. 모바일에서는 공개 사무실과 동기화된 기록만 보고, 원격 실행 연결은 별도 인증 중계 설계 후 추가한다.

## 3. 사무실 화면

상단에 **PC 연결 상태 / 출퇴근 / 오늘 근무 구간 / 남은 시간**을 표시한다. PC 연결과 AI 근무는 다른 상태다. 퇴근해도 서비스가 켜져 있으면 기록 열람은 가능하다.

직원을 선택하면 프로필 아래에 지시 입력란을 표시한다.

| 항목 | 동작 |
| --- | --- |
| 담당 | 선택한 직원. 대표는 총괄에게 지시 가능 |
| 프로젝트 | 사전에 PC에 등록한 작업공간 선택. 임의 경로 입력 금지 |
| 업무 내용 | 자연어 명령과 필요한 첨부 자료 |
| 실행 범위 | 초안 작성 / 프로젝트 수정. PC에서 허용한 범위만 표시 |
| 업무 지시 | PC가 업무를 저장한 뒤 접수 완료 표시 |
| 추가 지시 | 원래 업무에 연결된 후속 작업 생성 |
| 중단 | 현재 실행 중단 요청. 중단 확인 전에는 ‘중단 요청 중’ 표시 |
| 결과 보기 | 초안·변경 파일·테스트 결과·제약 표시 |

PC 미연결이면 지시 버튼 대신 연결 안내를 보여주고 입력 중인 내용은 임시 보관한다. 작성한 명령을 접수한 것처럼 표시하지 않는다. 오프라인 중 명령은 자동 실행 예약하지 않는다. 재연결 후 사용자가 한 번 제출한다.

## 4. 역할과 실행 범위

6개 직원은 서로 다른 역할 지침·담당 업무·결과 양식을 가진다. 아바타 수만큼 Codex를 동시에 실행한다는 뜻은 아니다. 초기에는 **한 번에 하나의 실제 작업**만 실행한다. 나머지는 대기한다.

| 직원 | 기본 결과 | 실행 권한 |
| --- | --- | --- |
| 총괄 | 작업 분해, 우선순위, 완료 기준, 보고 | 초안. 하위 업무는 보드에 제안하고 대표가 일괄 지시 가능 |
| 기획 | 요구사항, 고객 문제, 기능 명세 | 초안 및 지정 문서 |
| 개발 | 코드·기능·테스트·자동화 도구 | 등록 프로젝트의 격리 작업공간 수정 |
| 디자인 | 화면 코드, 콘텐츠, 디자인 명세 | 등록 프로젝트의 격리 작업공간 수정 |
| 마케팅 | 홍보 문안, 실험안, 판매 자료 | 초안. 외부 발송·광고 결제는 별도 승인 |
| 데이터·운영 | 분석 코드, 지표, 보고서 | 등록한 자료와 격리 작업공간 |

직원별 기본 권한 안의 가역적인 작업은 명령 한 번으로 진행한다. 매번 확인창을 띄우지 않는다. 배포·외부 발송·결제·보호된 브랜치 병합은 준비된 결과를 보여준 뒤 해당 행동에 대한 승인으로 구분한다.

v0.5는 초안 작성만 구현되어 있다. 프로젝트 수정 권한은 아래 2차 구현이 끝난 뒤 제공한다.

## 5. 업무 상태와 복구

상태: 대기 → 실행 중 → 검토 대기 → 완료. 예외 상태는 한도 대기, 실패, 중단 요청 중, 중단이다. 검토 대기와 완료를 구분한다. 회사 업무 완료는 결과 확인을 거쳐 표시한다.

- 제출마다 클라이언트 업무 ID를 만들고 PC DB의 고유 키로 저장한다. 버튼 중복 클릭이나 응답 유실 후 재제출도 동일 업무를 두 번 실행하지 않는다.
- 브라우저를 닫거나 새로고침해도 이미 접수된 작업은 PC에서 계속한다. 다시 연결하면 DB에서 상태와 결과를 읽는다.
- PC 종료 후 재시작하면 실행 중이던 업무를 ‘중단’으로 복구한다. 완료된 작업을 무조건 다시 실행하지 않는다.
- Codex 세션 ID와 이벤트 순번을 로컬에 보관한다. ‘계속 진행’은 명시적인 사용자 행동이며 이전 지시·결과·변경 파일을 재확인한다. SDK/CLI 재개 기능은 구현 시 공식 문서와 실제 동작을 검증한다.
- 결과가 로컬에 저장되면 GitHub 동기화 실패와 무관하게 사무실에서 확인 가능하다. 동기화 실패는 별도 표시하고 다시 전송한다. AI 작업을 재실행하지 않는다.
- 웹 연결 끊김은 PC 종료의 증거가 아니다. 연결 상태는 ‘연결 끊김’으로 표시하고 재연결 후 실제 작업 상태를 조회한다.

## 6. 근무 정책

한국 날짜 기준 최대 5시간 근무 구간 2회다. PC 서비스 시작만으로 구간을 소비하지 않고, 사무실에서 출근할 때 시작한다. 같은 구간에 재접속하면 남은 시간을 이어 쓴다. 자정에 해당 날짜의 구간을 종료한다.

구간 종료 시 새 작업은 시작하지 않는다. 실행 중 작업은 시간 내 체크포인트를 남기고 중단하도록 요청한다. 제한 시간까지 끝나지 않으면 프로세스 트리를 종료하고 ‘중단’으로 기록한다. 다음 구간은 사무실의 ‘다음 근무 시작’으로 연다.

Codex의 실제 사용량 제한과 회사 근무 시간은 별개다. 5시간 후 한도 복구를 가정하지 않는다. 한도 도달 시 ‘한도 대기’로 멈추고, 공식 응답으로 확인할 수 있는 복구 시각만 표시한다. 시각을 알 수 없으면 ‘복구 시각 미확인’으로 표시한다. 유료 API로 자동 전환하지 않는다.

## 7. 로컬 API 계약 초안

모든 업무 API는 연결 인증을 요구하며 요청·응답에 버전을 포함한다. 명령 본문은 JSON이고 크기 제한을 둔다. 브라우저가 임의 셸 명령을 직접 전달하는 API는 만들지 않는다.

| 요청 | 목적 | 주요 응답 |
| --- | --- | --- |
| `GET /health` | 서비스 존재·버전 확인. 민감 정보 없음 | 프로토콜 버전 |
| `POST /pair/request` | 연결 요청, PC에서 로컬 승인 | 대기 중인 연결 ID |
| `POST /pair/complete` | 일회용 연결 증명 확인 | 짧은 수명의 세션 토큰 |
| `GET /v1/office` | 연결·근무·직원·작업공간 조회 | 구간, 시간, 상태 |
| `POST /v1/attendance/start` | 출근·다음 구간 | 근무 종료 시각 |
| `POST /v1/attendance/stop` | 퇴근 및 실행 중단 | 처리 중 또는 퇴근 |
| `POST /v1/tasks` | 업무 접수 | `task_id`, 상태, 접수 시각 |
| `GET /v1/tasks?after=...` | 상태·로그·결과 증분 조회 | 이벤트 순번, 업무 목록 |
| `POST /v1/tasks/{id}/cancel` | 중단 요청 | 중단 요청 중 |
| `POST /v1/tasks/{id}/followups` | 추가 지시·재개 | 후속 업무 ID |
| `POST /v1/tasks/{id}/review` | 검토 의견·완료 처리 | 검토 상태 |

일단 짧은 간격의 인증된 조회로 구현한다. WebSocket/SSE는 상태 복구와 브라우저 인증 제약을 검증한 후 필요할 때 추가한다. 로그는 ‘파일 수정 중’, ‘테스트 실행 중’ 같은 실행 증거를 보여주며 모델의 비공개 사고 과정을 요구하지 않는다.

## 8. 연결 인증과 실행 경계

- 최초 연결 시 PC 실행기에서 실제 요청을 확인하고 승인한다. 일회용 증명은 짧게 만료하며 무제한 시도를 막는다. 승인 전에는 작업·파일 조회와 실행을 허용하지 않는다.
- 웹용 연결 토큰은 Codex/GitHub 토큰과 다르다. 세션 메모리에만 보관하고 URL·공개 기록·localStorage에 남기지 않는다. 새로고침 후 안전하게 재연결한다. PC에서 연결 철회 가능하게 한다.
- Host와 Origin을 확인하고 CORS는 허용 출처에만 응답한다. `*`, `null` 출처, 임의 호스트는 허용하지 않는다. 쓰기 API는 인증 헤더와 JSON을 요구한다. 외부 사이트의 단순 폼 요청은 업무를 만들 수 없다.
- GitHub Pages의 출처는 `https://ryemso.github.io`다. 같은 계정의 다른 프로젝트도 같은 출처를 공유한다. URL의 `/my_little_office/` 경로만으로 브라우저 출처를 분리할 수 있다고 가정하지 않는다. 로컬 승인·세션 인증을 함께 적용하고, 독립 출처가 필요하면 전용 도메인을 사용한다.
- Codex 인증은 공식 로컬 저장소에 유지한다. 웹 페이지로 토큰을 전달하지 않는다. 프로젝트 변경은 허용 목록의 작업공간 ID만 받는다. 경로 탈출·심볼릭 링크·임의 실행 파일 지정은 차단한다.
- 프로젝트 수정은 별도 git worktree/작업 브랜치에서 진행한다. 기존 미커밋 변경을 덮어쓰지 않는다. 읽기/쓰기 샌드박스를 작업 모드에 맞춰 적용하며 실패 시 더 넓은 권한으로 자동 재시도하지 않는다.
- 테스트 실행은 프로젝트 수정 모드의 권한 안에서만 허용한다. 생성 코드·프로젝트 스크립트가 PC의 모든 파일이나 인증 정보에 접근하지 않도록 실행 경계도 검증한다. 샌드박스 이름만으로 완전한 격리를 보장하지 않는다.

## 9. 기록과 GitHub 저장

프로젝트 코드·설계·결정·개발 이력은 기존 저장소에 계속 저장한다. 실시간 원본 업무 DB는 PC에 두고, 공개 작업의 지시·최종 결과·검토·변경 커밋은 GitHub에 동기화한다. 공개 예정임을 입력 화면에 표시한다. PC 내부 경로·인증 자료·원문 오류 로그는 공개하지 않는다.

GitHub 업로드 성공을 AI 작업 성공 조건으로 삼지 않는다. 사무실은 `작업 결과`와 `GitHub 저장 상태`를 분리해서 표시한다. 공개 기록에는 실제 실행한 근거와 검증 범위를 적으며 가상의 매출·성공 기록을 만들지 않는다.

## 10. 구현 순서와 통과 기준

### 1차: 복사 없는 초안 실행

로컬 연결 서비스, 연결 승인, 사무실 직접 접수, SQLite 큐, Codex 초안 실행, 상태·결과 표시, 출퇴근을 연결한다. GitHub 수동 접수는 기존 호환 경로로만 남긴다.

완료 기준:

- Pages 사무실에서 지시한 한 개 업무가 PC에서 한 번 실행되고 같은 화면에 결과가 표시된다.
- 외부 입력창에 복사하거나 GitHub Actions를 수동 실행하지 않는다.
- PC 미연결, 새로고침, 중복 클릭, 네트워크 단절, 작업 실패, 강제 종료, 한도 도달을 각각 구별한다.
- 허용되지 않은 웹 출처·무인증 요청·만료된 연결로 작업을 만들 수 없다.
- Chrome/Edge의 실제 연결·권한 거부와 로컬 사무실 대체 경로를 검증한다.
- 실제 Codex 검증은 사용자의 PC에서 로그인한 뒤 수행한다. 모의 테스트만으로 실제 연결 완료라고 보고하지 않는다.

### 2차: 프로젝트 파일 수정과 테스트

PC에서 프로젝트를 한 번 등록하고, 개발·디자인 직원에게 수정 모드를 연다. 사무실에서 명령 → 격리 작업공간 변경 → 테스트 → 파일 차이와 결과 검토까지 연결한다. 완료 기준은 지정 프로젝트에서 한 개 기능 변경과 테스트 결과가 확인되고 원래 작업공간의 미커밋 변경이 유지되는 것이다.

### 3차: 여러 직원의 업무 이어받기

총괄의 작업 분해 → 기획 명세 → 개발 구현 → 데이터 검증을 보드에서 연결한다. 초기에는 대표가 준비된 하위 업무를 한 번에 지시하고, 작업 루프·요청 수·근무 시간 제한을 둔다. 실제 병렬 실행과 자동 외부 행동은 별도 검증 후 확장한다.
