# My Little Office 실행·승인 구조 재설계

작성: 2026-10-23 / 상태: v0.19 승인 왕복 구현 / 실제 PC 브라우저 인수 전
기준: v0.18 1차 구현과 직원 브라우저 접근 거절 기록
목적: 지시 → 실제 도구 실행 → 필요한 사용자 확인 → 이어서 실행 → 결과 검증을 사무실 안에서 연결한다.

## 1. 결론과 결정

픽셀 사무실 UI, SQLite, 업무·인계·예약, 기존 게시 승인, 네이버 Playwright adapter를 보존한다. 직원의 대화형 업무 실행을 현재 단발성 CLI 호출에서 양방향 Runtime Adapter로 전환한다. 우선 후보는 Codex app-server의 로컬 stdio 연결이다. 외부 서버, Supabase, 새로운 프런트엔드 프레임워크 도입은 이번 문제의 선행 조건이 아니다.

단, app-server 도입과 브라우저 origin 승인 성공을 동일시하지 않는다. 실제 승인 이벤트가 지원되는 프로토콜로 전달되는지 먼저 실험한다. 앱 밖의 제품·확장 프로그램에서만 처리 가능한 동의라면 해당 공식 화면으로 안내하고 확인할 때까지 대기한다. 권한 거절을 다른 도구로 우회하지 않는다.

## 2. 확인된 사실과 가설

| 구분 | 사실/가설 | 근거 또는 확인 방법 |
|---|---|---|
| 코드 확인 | office/engine.py는 codex exec를 실행하고 프롬프트를 쓴 후 stdin을 닫는다 | subprocess 생성과 stdin.close 호출 |
| 코드 확인 | stdout/stderr는 파일로 받고 진행 로그를 읽는다 | 현재 실행 루프 |
| 코드 확인 | 앱의 대표 승인함은 작업 승인·검토용이며 runtime RPC 승인 요청 응답 구현이 없다 | office/inbox.py 및 web_server.py |
| 사용자 제출 기록 | 탭 목록은 조회되지만 127.0.0.1:8501 origin 접근은 도구가 거절했다 | 직원 보고서에 인용된 도구 응답; 원본 로그 독립 대조는 아직 안 함 |
| 사용자 화면 | Chrome 확장 프로그램은 모든 사이트 접근으로 설정됐다 | 제공 스크린샷; AI 도구의 별도 동의까지 승인했다는 증거는 아님 |
| 미확정 | 비대화형 실행 또는 승인 처리 부재가 이번 거절의 직접 원인이다 | 실제 CLI 버전·유효 정책·승인 이벤트 대조 필요 |
| 미확정 | 브라우저 origin 요청이 MCP elicitation으로 노출된다 | 동일 도구의 원본 요청/응답과 app-server 실험 필요 |
| 미확정 | Work와 회사 직원이 같은 브라우저 도구·정책·호스트를 사용한다 | 이름만으로 같다고 판단하지 말고 연결 메타데이터 비교 |

stdin을 열어 두기만 하면 codex exec가 대화형 승인 프로토콜이 되는 것은 아니다. stdin.close는 현재 일방향 구조를 보여주는 증거이며, 그 한 줄을 제거하는 수정으로 끝내지 않는다. 단순히 승인을 전부 허용하거나 샌드박스를 해제하지 않는다.

## 3. 해결 범위

첫 목표는 Google 로그인이 아니다. 같은 Windows PC에서 대표가 지정한 로컬 페이지에 대해, 실제로 발생한 승인 요청을 표시하고 사용자의 응답 후 그 요청이 처리되는지 확인한다. 이후 로그인, 게시, 반복 업무 순으로 넓힌다.

첫 실험은 사무실 자체 화면 대신 민감정보 없는 작은 로컬 검증 페이지도 사용할 수 있다. 단, 기존 거절의 대체 경로로 사용하지 않는다. 독립 테스트 대상으로 명시적으로 승인받은 페이지에서 통신 흐름만 검증한다. 실제 사무실 origin에 대한 거절은 그대로 유지하고 별도로 해결한다.

이번 설계는 기존 ChatGPT 대화방·로그인 계정·연결 도구가 회사에 자동 이전된다고 가정하지 않는다. 개발용 로그인 모형과 실제 OAuth를 UI·문서·완료 조건에서 구분한다.

## 4. 구성과 책임

| 구성 | 책임 | 보존/변경 |
|---|---|---|
| 웹 사무실 | 업무 입력, 진행, 대표 알림, 승인 카드, 결과 확인 | 기존 UI 확장 |
| Office Orchestrator | 의존 업무 관리, 실행 시점과 중단·재개 결정 | 상태 모델 보완 |
| Runtime Adapter | 요청·응답·이벤트, thread/turn 관리, 취소, 프로세스 생명주기 | 신규 추상화 |
| Exec Adapter | 승인 입력이 필요 없는 기존 작업 수행 | 선택적 호환 경로로 보존 |
| App-server Adapter | 양방향 직원 실행, 지원되는 서버 요청 전달 | 호환성 검증 후 추가 |
| Approval Broker | 요청 보관, 사용자 응답 검증, 원 요청으로 전달, 해결 확인 | 신규 |
| Browser Capability Registry | 도구·브라우저·기기·origin·계정 연결 상태 확인 | 신규 |
| Browser adapters | 허용된 사이트의 조작, 세션, 게시 결과 확인 | 네이버 기존 코드 재사용 |
| Result Validator | 과업별 실제 완료 증거 검증 | 기존 파일 검증을 보완 |

전체 조직을 한 번에 새 실행기로 바꾸지 않는다. 한 직원·한 업무·한 프로세스부터 검증한다. 직원 수나 아바타가 도구 권한을 대신하지 않는다.

## 5. 연결 프로토콜 방침

공식 문서 근거: https://learn.chatgpt.com/docs/app-server

app-server는 양방향 요청/응답과 이벤트를 제공한다. 구현 시 설치된 CLI의 버전을 기록하고 그 버전에서 생성한 JSON schema로 메시지 형식을 확정한다. 현재 문서의 필드가 사용자 PC의 0.163.0에 동일하다고 가정하지 않는다. 기능의 실험적 상태와 버전 차이를 전제로 기능 플래그 및 이전 실행기 복귀 경로를 유지한다.

우선 대응할 요청 종류는 명령 승인, 파일 변경 승인, MCP elicitation, 사용자 입력, 권한 요청이다. 원본 method와 request ID를 보존하고 종류별 지원되는 응답만 보낸다. URL 인증형 요청은 사용자 화면에서 절차를 마치게 하며 단순 버튼 클릭만으로 인증 완료 처리하지 않는다. 알 수 없는 요청은 자동 승인하지 않고 지원되지 않음으로 표시한다.

이 문서의 업무 상태·API·DB 명칭은 회사 내부 제안이며 Codex의 실제 wire schema를 의미하지 않는다. 구현 전 호환성 실험에서 실제 요청 형태를 확정한다.

## 6. 실행 흐름

1. 대표가 과업과 대상·완료 조건을 지정한다.
2. 실행 전 CLI/인증/도구 연결/브라우저 계열/대상 기기를 확인한다. 비밀값은 수집하지 않는다.
3. 지원되는 실행기에서 thread와 turn을 시작하고 이벤트를 계속 수신한다.
4. 승인 요청이 오면 요청을 먼저 DB에 기록한 뒤 업무를 waiting_input으로 표시한다. 뒤 직원에게 같은 시도를 넘기지 않는다.
5. 대표 아바타 느낌표와 대화에 대상·이유·범위·요청 종류를 표시한다.
6. 대표 응답을 받은 뒤 프로세스 세대, 원본 요청 ID, 상태 버전, 허용된 선택지를 검증한다.
7. 같은 연결의 원 요청에 응답한다. UI는 전송 중으로 표시한다.
8. 실행기의 해결 통지나 해당 도구의 실제 결과가 확인돼야 대기를 해제한다. 버튼을 눌렀다는 사실만으로 READY로 바꾸지 않는다.
9. 실행이 끝나면 과업별 Validator를 통과해야 completed가 된다.

브라우저 접근 허용은 페이지 읽기·조작 범위의 동의이며 Google 인증·공개 게시·배포 승인과 별개다. 단일 승인 버튼으로 이들을 묶지 않는다.

## 7. 승인 카드 UX

표시 내용: 요청한 직원/업무, 대상 서비스와 origin, 브라우저/기기, 요청 동작, 필요한 이유, 일회성 범위, 현재 상태.

선택: 이번 요청 허용 / 거절 / 업무 중단. 세션 허용은 실행기가 실제 지원하고 범위가 명확할 때만 제공한다. 모든 사이트 영구 허용을 기본 옵션으로 만들지 않는다. 명령 승인에는 실행 명령·경로를, MCP 폼에는 검증된 스키마의 공개 필드만 표시한다.

추가 상태를 따로 표현한다:
- 사용자 응답 대기: 응답할 수 있는 살아 있는 요청이 있음.
- 외부 화면 확인 필요: 동의를 이 앱에서 전달할 수 없고 공식 화면에서 조치해야 함.
- 정책 차단: 현재 사용자가 앱 안에서 승인해도 해제할 수 없는 정책 거절.
- 연결 오류: 요청을 받거나 응답 전달에 실패함.
- 응답 전송 중: 클릭은 접수됐지만 실행기 처리 확인 전.

승인 대기 시간과 실행 타임아웃을 구분한다. 제안 기본값은 사용자 확인 최대 15분, 살아 있는 요청과 연결이 유지되는 동안 도구 실행 예산은 일시 정지다. 만료 시 지원되는 취소 응답을 보내고 expired로 기록하며 승인으로 간주하지 않는다. 자동 예약은 사용자 입력이 필요한 첫 지점에서 멈추고 후속 예약을 정지한다.

## 8. 상태와 완료 계약

업무 상태 제안: queued → running ↔ waiting_input → verifying → completed.
별도 종료/대기: policy_blocked, needs_setup, failed, interrupted, cancelled, unknown_outcome.
기존 review는 대표 결과 검토, awaiting_approval은 기존 외부 작업 승인으로 의미를 유지한다. runtime 입력 대기와 혼용하지 않는다.

승인 상태: pending → responding → accepted/declined/cancelled.
예외: expired, disconnected, superseded, delivery_unknown. 사용자 의사와 전달 결과는 별도 필드로 저장한다. 앱 재시작 후 이미 승인했다고 재전송하지 않는다. 이전 프로세스의 요청은 무효화하고 살아 있는 실행기와 대조한 새 요청만 사용자에게 제시한다.

| 과업 | 완료 조건 | 완료 증거가 아닌 것 |
|---|---|---|
| 브라우저 접근 | 지정 origin의 본문 관찰 결과 | 탭 목록·보고서 생성 |
| 로그인 | 대상 앱 복귀 및 계정/세션의 비밀값 없는 확인 | 로그인 버튼 클릭·인증 화면 도달 |
| 분석 | 입력 검사·코드 실행·결과값 검사 | 분석 계획서 |
| 초안 저장 | 원격 저장 후 다시 읽은 제목·본문/이미지 검사 | 저장 버튼 클릭 |
| 게시 | 승인 원문과 일치하는 원격 결과 확인 | 발행 클릭·URL 문자열만 생성 |
| 거절 대응 | denied/blocked 상태와 사용자 알림 기록 | 원래 로그인 업무 completed |

‘접근 성공 또는 거절 보고서 작성’을 하나의 성공 조건으로 묶지 않는다. 진단 업무는 진단 완료로 끝날 수 있지만 상위 로그인 목표는 blocked 상태를 유지한다. 총괄 보고서의 문서 검증으로 그 목표를 완료 처리하지 않는다.

## 9. 저장 모델과 API 제안

runtime_sessions: id, task_id, adapter, cli_version, schema_digest, process_epoch, thread_id, turn_id, state, heartbeat_at.
input_requests: id, session_id, process_epoch, rpc_request_id_json, method, category, sanitized_payload_json, scope_digest, status, version, created_at, expires_at.
input_decisions: id, request_id, version, actor, choice, decided_at, delivery_state, resolved_at.
capability_checks: id, task_id, tool_id, browser_family, device_alias, origin, status, reason_code, checked_at.
run_events: id, task_id, session_id, sequence, event_type, safe_payload_json, created_at.

프로세스 세대와 RPC ID를 함께 식별키로 사용한다. 새 프로세스에서 같은 request ID가 재사용돼도 이전 승인으로 처리하지 않는다. JSON RPC ID의 원래 타입도 보존한다.

내부 API 제안:
- GET /api/runtime/requests: 대표가 처리할 요청의 안전한 표시.
- POST /api/runtime/requests/{id}/decision: version·choice·scope_digest 검사 후 한 번만 접수.
- POST /api/runtime/tasks/{id}/interrupt: 살아 있는 턴 중단.
- GET /api/runtime/tasks/{id}/capabilities: 대상별 연결·승인 상태.

기존 loopback 바인딩, Origin 검사, 연결 토큰을 유지한다. 승인 API는 대표 권한 확인과 재전송 방지 검증을 포함한다. 동시 클릭은 DB의 compare-and-swap으로 한 번만 수락한다. 입력 폼이나 URL의 토큰·쿠키·비밀번호는 로그 및 공개 UI에 저장하지 않는다. 외부 페이지 문구는 승인 근거가 아니라 신뢰하지 않는 데이터다.

## 10. 권한과 연결의 구분

Chrome 확장 사이트 권한, AI 브라우저 origin 동의, Codex 실행 정책, Windows 파일/프로세스 권한, 서비스 로그인, 게시 승인, Pages→PC 연결을 각각 표시한다. 하나가 정상이라고 나머지를 정상 처리하지 않는다.

도구 우선순위는 기능 이름으로 정하지 않는다. 해당 업무에 실제 연결된 공식 도구를 사용한다. 거절을 다른 브라우저·Playwright·셸로 갈아타 해소하지 않는다. 서비스별 독립 Playwright adapter는 사전에 정한 자체 업무 경로로만 사용하며 기존 거절을 우회하는 재시도 경로로 쓰지 않는다.

Work의 내부 브라우저 연결을 회사에서 동일하게 재현할 수 있는지는 별도 호환성 항목이다. app-server는 승인 전달의 후보이지 Work 전용 도구를 회사에 제공하는 제품이 아니다.

## 11. 구현 전 필수 진단 (D0)

수집: Codex 실제 버전/실행 옵션, 비밀값을 제외한 유효 승인 정책, 도구 이름/버전/연결 상태, 원본 오류 코드, 요청 발생 시각, approval/elicitation 이벤트 존재 여부, 사용자 UI 요청 표시 여부. 토큰·설정 파일 전체·브라우저 세션 원본은 수집하지 않는다.

다음 세 경우로 판정한다:
A. 요청이 실행기에 도달하고 응답 경로만 없음 → Approval Broker 구현으로 진행.
B. 요청이 app-server 밖 제품에만 표시됨 → 공식 호스트 동의 흐름을 안내하는 integration 필요. 앱에서 허용했다고 가짜 승인하지 않음.
C. 상위 정책의 고정 거절 → 설정 주체·허용 가능한 변경을 명확히 안내. 실행기는 우회하지 않고 정책 차단 유지.

D0의 직접 원인 확인 전에도 모의 RPC 전송과 UI를 만들 수 있지만 ‘실제 브라우저 차단 해결’이라고 출시하지 않는다.

## 12. 단계별 작업과 인수 기준

| 순서 | 작업 | 통과 기준 |
|---|---|---|
| D0 | 원본 거절·유효 정책·버전과 capability 조사 | A/B/C 판정, 근거·미확인 항목 기록 |
| D1 | 버전 고정 Runtime Adapter와 가짜 RPC 서버 | 초기화·이벤트·동시 RPC·요청 ID 매칭·중단 검사 |
| D2 | Approval Broker DB/API | 이중 클릭·늦은 응답·타임아웃·프로세스 단절에서 잘못된 승인 없음 |
| D3 | 대표 느낌표와 카드 연계 | 요청 발생→표시→응답→해결 확인까지 모형 통과 |
| D4 | 실제 Codex의 지원되는 승인 요청 1건 | 거절·허용 각각 실제 처리되고 이벤트로 확인 |
| D5 | 실제 브라우저 origin 승인 | 사용자 동의 후 본문 접근 성공; 정책 거절과 UI 대기 분리 |
| D6 | 서비스 로그인·기존 게시 adapter 통합 | 로그인 복귀·원문 승인·중복 방지·불확실 결과 재게시 금지 |
| D7 | 직원 인계·예약·재시작 회귀 | 대기 중 후속 실행 없음, 재시작 후 예전 승인 재사용 없음 |

D5 실패 시 D6의 브라우저 업무를 성공 출시하지 않는다. 일반 분석·문서 업무는 검증된 기존 경로로 유지한다. 실제 Google OAuth는 대상 앱·정확한 URL·로그인 목적을 확정한 별도 작업으로 검증한다.

## 13. 최소 검증 시나리오

- 허용/거절/취소/정책 고정 거절/지원하지 않는 요청을 구분한다.
- 2개 동시 요청에서 A의 클릭이 B에 전달되지 않는다.
- 두 브라우저 화면에서 같은 요청을 눌러도 실행은 한 번이다.
- 허용 클릭 직후 프로세스가 죽으면 허용 완료라고 표시하지 않는다.
- 연결 단절 후 RPC ID가 같아도 다른 프로세스에 이전 승인을 보내지 않는다.
- 요청 내용·origin·계정·승인 원문이 바뀌면 새 검토를 요구한다.
- 사용자가 아무 응답도 하지 않으면 승인하지 않는다.
- MCP 폼/URL에 비밀값이 들어가도 대화·DB·감사 로그로 노출되지 않는다.
- 접근 거절 후 다른 직원/도구로 동일 작업을 우회하지 않는다.
- 원격 저장·발행의 결과 불명 상태를 자동 재시도하지 않는다.
- 문서 3개가 생성돼도 로그인 증거가 없으면 로그인 업무는 완료되지 않는다.
- Pages·로컬 같은 UI, 기존 DB·네이버·GitHub 승인·분석 검증 기능이 유지된다.

## 14. 다음 구현 단위

우선 D0 진단과 D1~D3의 모의 승인 왕복을 구현한다. 성공 화면은 ‘실행 중 권한 요청 1건을 대표가 응답하고 직원이 그 결과를 받아 이어서 일하는 것’으로 한정한다. 공통 사이트 자동 로그인, 기존 GPT 대화방 조작, 전 서비스 자동 게시를 한 번에 구현 목표로 잡지 않는다.

설계 완료와 구현 완료, 모형 통과와 Windows 실사용 통과, 로그인과 게시 완료를 각각 다른 상태로 보고한다.


## 구현 추적
